# Design

## Context

参见 `proposal.md` 的 Why；外部行为以四份增量 spec 为准。

- 后端为 Spring Boot、MyBatis-Plus、MySQL、Flyway；目前最高迁移为 V6。管理端 JWT 统一带 `ADMIN` role，SecurityConfig 对 `/api/v1/admin/**` 只做粗粒度角色保护，admin_account 只有启停状态，没有店主/店员及权限模型。
- 现有业务表已保存下单、成功支付、退款、已退商品数量、SKU 实物与预留库存；支付和退款分别有事件时间。订单状态统计可读 shop_order 当前状态。
- `AuditService` 写入 `admin_operation_log`，该表主键被库存流水外键引用，历史数据需继续保留。当前成功业务审计缺少登录、IP、请求路径和目标摘要，且登录失败不会留痕。
- 前端已有管理布局和路由守卫，但所有管理员共用同一权限；首页目前展示静态视觉区域，无运营轮播和公告。前端依赖中没有图表库。

## Goals / Non-Goals

**Goals:**

- 以单店现有业务表提供可复核的统计结果，并让统计、身份权限、审计与首页内容共享一致的日期及访问控制规则。
- 让角色、模块权限和敏感操作权限在所有服务端入口生效；店主授权无需依赖 token 中长期缓存的权限快照。
- 在不破坏库存流水和已有操作记录的前提下补足审计字段，覆盖既有及新增管理写操作。
- 让内容的发布时间窗口直接决定公开可见性，不依赖定时任务准时修改发布状态。

**Non-Goals:**

- 不引入数据仓库、缓存预计算、异步消息平台、多店铺、财务结算、异常监控告警、日志导出或可配置保留策略；审计日志固定保留 7 天后自动清理，被库存流水引用的日志除外。
- 不允许店员创建或管理其他店员，也不允许店员查看系统审计日志。
- 不改变已有订单、售后、退款和库存状态机的业务含义。

## Decisions

### 1. 后台身份与权限模型

在 `admin_account` 增加账号类型及凭证版本字段。既有管理员迁移为 `OWNER`，后续 AdminBootstrap 新建的初始账号也为 OWNER；店员复用该账户表，以 `STAFF` 类型及状态参与登录。店员模块授权和高影响操作授权使用独立关系表存储，不把可变权限集合放在 JWT 或逗号分隔字段中。店主拥有全权限且是唯一可调用员工账户/权限管理 API 的身份；账户及权限变更必须审计，没有“店员权限管理”开关。

JWT 只证明已认证的后台主体及其 account id。管理请求到达后从数据库确认账号仍启用并解析当前 account type/permission，禁止仅信任 token 内的旧权限。保留后台 principal 的 ADMIN 安全域以兼容现有 `/admin` 路由结构，由集中式授权服务对具体 API 执行 OWNER、模块权限和敏感操作权限检查；所有 Admin Controller 必须显式归属一个权限域，未分类接口默认拒绝。`/admin/auth/login` 保持公开，`/me` 返回当前账号类型与权限以驱动前端导航。

权限域按现有 API 分组：商品及分类/评价、买家、订单、库存、售后、内容、统计。日志与员工/权限管理仅 OWNER 可访问。敏感操作单独使用退款执行、商品上下架、库存直接调整三类开关；其检查同时要求对应模块权限。库存直接调整涵盖库存单据过账、盘点、阈值/实物维护和新增 SKU 初始库存；订单发货及售后验收按各自订单/售后模块授权执行，其库存变化仍由既有履约/售后事务产生，不另走人工调整权限。

备选方案是只在前端隐藏菜单或把所有权限冻结在 JWT 中；前者不能防 API 直调，后者在撤权后仍有令牌有效期窗口，因此均不采用。若每个请求查询账户权限对性能产生可观测影响，再在不延迟撤权的前提下评估短期可失效缓存。

### 2. 管理 API 改造与前端权限呈现

在现有 `/api/v1/admin/**` API 上按读写端点补充模块授权；对上述敏感写端点叠加独立权限验证。员工管理 API 仅供 OWNER：分页查询、创建、修改资料/权限、停用/启用及重置凭证，不提供硬删除。权限保存采用完整集合替换并在事务中验证枚举和账号状态；店员不能通过提交未知权限或直接调用接口扩大权限。

前端根据 `/me` 权限显示菜单及动作按钮，owner-only 页面仅对店主显示。页面隐藏是交互优化，后端仍返回统一 401/403 并保证拒绝路径无业务副作用。对敏感按钮提示操作影响并在成功/拒绝状态中保留用户输入。登录后的导航和路由守卫区分 OWNER/STAFF，但最终权限以服务端为准。

### 3. 审计日志扩展与兼容

保留现有 `admin_operation_log` 表和主键，避免破坏 `inventory_movement.operation_log_id` 外键；通过后续迁移为其增加事件分类、账号名快照、来源 IP、请求路径、目标摘要及失败类别等字段，并允许未知账号的登录失败记录没有 admin_id/target_id。扩展结果枚举以表达失败和拒绝。为账号、时间、类型、结果、目标建立查询索引。已有行保持原样，可用可空新增字段呈现为“历史业务操作”，不伪造来源 IP 或路径。

扩展 AuditService 作为成功业务变更的同事务写入点；覆盖现在未调用 audit.record 的后台写 API。认证成功/失败与授权拒绝在请求主体事务之外通过独立事务记录，防止失败回滚抹去安全事件；成功业务及其审计必须同事务提交，审计写入失败时业务写入回滚。审计查询仅 OWNER 可用，按时间倒序稳定分页，允许筛选操作者、类别、结果、目标及时间区间。不得记录请求正文、密码、散列、token、Authorization header 或完整身份凭据。来源 IP 取连接地址；只有配置了可信代理时才解析代理头，不能直接信任客户端自带的 `X-Forwarded-For`。

活跃买家口径还需要成功登录事件，因此仅为买家成功认证增加轻量活动记录（买家 id 与成功时间），不将买家认证失败或凭据内容暴露到店主管理日志。该记录只用于聚合统计，不提供个人登录明细页面。

备选方案是另建一套审计表并迁移/复制所有历史操作；保留被库存流水引用的现表更小且能连续展示旧记录。新增字段不回填未知历史信息。

### 4. 经营统计查询

新增管理统计 API 和专用只读聚合 mapper，使用带日期边界的 SQL 聚合，不把明细全量加载到 Java 内存。共享参数解析层将日期按 Asia/Shanghai 解析成左闭右开时间戳；快捷区间包含当天，本周周一开始，最近 30 个日历日包含今天，自定义日期端点均为包含日。每日、周一开始每周、每月生成完整时间桶，缺失桶返回零。

- 订单量按 `shop_order.created_at` 归属时间桶，状态分布在该创建区间内按订单当前状态计数。
- 销售金额按 `payment_record.result=SUCCESS` 的支付金额和支付时间计正值，按成功退款记录金额和退款时间计负值。销售件数只统计成功支付订单的商品数量，并按退款事件时间扣减相关售出商品数量；支付失败/待付不产生销售。现有退款记录关联售后明细，可用退款请求对应的商品行核对数量，不能把一次付款重试重复计入商品件数。
- 注册量按买家账号创建时间统计。活跃买家为成功登录活动与 `shop_order.created_at` 区间内买家的 distinct union，订单不要求已支付。
- 热销榜按区间净售件数倒序，展示净销售额并用 product id 稳定排序；库存榜按当前 `on_hand - reserved` 可售件数倒序。排除逻辑删除商品，榜单条数由接口限制且默认 10。

第一版使用实时数据库查询，按支付/退款时间、订单创建时间、成功登录活动时间及 SKU 关联查询计划验证索引；Flyway 新增必要索引。前端新增 ECharts 绘制趋势与状态图，并将图表所需点位与概览数值从统计接口取回；空数据返回零值/空数组，不能用前端模拟数值填补。

备选方案是定时汇总表/缓存；当前项目规模和数据规模尚无容量证据支持额外一致性机制，先保持实时口径，查询负载成为实测瓶颈后再独立规划预聚合。

### 5. 轮播图、公告与图片存储

新增轮播图和公告实体及对应管理/公开 API。两类内容独立维护启用状态、发布时间窗口和排序；公告另有置顶、正文和摘要。公开查询在数据库条件中直接应用 enabled、`start_at <= now`、`end_at IS NULL OR end_at > now`，按配置排序并用 id 消歧义；公告详情对未发布内容统一返回 not found，避免 ID 探测泄露草稿。不存在需要准时改变数据库状态的定时任务。

轮播图复用现有经过 MIME、文件签名和图像解码校验的图片上传与公开图片读取能力，通过存储键引用已上传资源；扩展上传入口权限为 OWNER 或具备 content 模块权限的店员，并保证商品图片绑定流程不会误绑定/删除作为轮播资源的文件。轮播跳转目标限定为站内相对路径或 http/https URL，拒绝 javascript/data 等活动内容协议。公告列表返回标题、摘要、置顶及发布时间，详情返回正文。

备选是将轮播图二进制放入数据库或另建上传管线；复用现有文件校验和服务减少重复风险。公告详情和列表分别提供接口，避免首页加载全部长正文。

### 6. 数据库迁移和前端页面

在 V6 之后增加一个或多个单调递增 Flyway 迁移：扩展管理员账号与权限表，扩展操作日志字段和索引，增加买家成功登录活动记录、内容表及统计所需索引。旧管理员全部迁为 OWNER，保留账号 id、哈希、状态及既有日志/库存流水。同步 H2 测试 schema 和迁移测试；不修改 V1–V6。

前端按现有 Vue Router、API wrapper、PageStatus、分页等约定，新增统计工作台、店员与权限、审计日志、轮播图/公告管理视图；后台导航按当前账号权限过滤。首页以响应式轮播区、公告列表与公告详情承载公开内容；网络错误/空内容使用现有状态交互，不回退展示后台草稿。新增 ECharts 为图表依赖。

### 7. 测试策略

后端集成测试覆盖旧库升级、店主迁移、店员各模块允许/拒绝、敏感操作二次授权、旧 token 撤权/停用、权限写入审计、登录成功/失败、未知账号及脱敏、失败审计持久化、聚合多支付/退款/部分退款、日期边界和无数据、定时内容可见窗口与图片权限。

前端验证权限菜单及直接路由、图表日期/粒度切换、筛选分页、创建/编辑/排序/定时发布流程和拒绝错误；桌面及窄屏检查图表、表格、公告详情和首页轮播布局。端到端验证只使用隔离数据，不改变真实业务记录。

## Risks / Trade-offs

- [每个后台请求查询当前权限增加数据库读取] → 使用索引化的小型权限映射查询；先测量再决定缓存，任何缓存必须支持即时撤权。
- [现有管理员 token 声明只有 ADMIN] → 管理员会话解析以数据库账号类型为准；部署迁移后要求旧会话刷新或在服务端进行账号状态检查，不根据旧 token 的权限快照放行。
- [历史审计字段不完整] → 保留原记录并将新增字段留空，不臆造 IP、路径或操作者快照。
- [实时统计随历史数据增长变慢] → 限定只读聚合、校验索引和查询计划；如实测仍超出响应目标，再单独评估按日预聚合。
- [ECharts 增加前端包体] → 仅按需加载图表模块，确认打包体积和页面性能。
- [定时发布受客户端和服务器时钟差异影响] → 数据库统一时区配置，日期边界在 Asia/Shanghai 解析并通过时间边界集成测试。
- [审计 IP 可能经代理转发不可信] → 默认记录连接来源；只有显式配置的可信代理地址才允许采用转发头。
- [轮播图片上传后未被任何内容引用] → 沿用未绑定图片生命周期并提供可追踪的图片记录；是否支持自动清理由后续独立策略决定，本次不自动删除资源。

## Migration Plan

1. 确认部署目标已应用至 V6；新增后续 Flyway 迁移和 H2 schema，创建角色/权限/活动/内容结构并为现有管理员设置 OWNER；扩展日志而不改动历史流水外键。
2. 在可丢弃 MySQL 库上从旧版本升级，验证所有管理员可登录为 OWNER，原密码哈希、历史日志、库存流水及业务数据保持不变。先部署数据库兼容版本，再部署后端和前端。
3. 发布后端后验证默认管理员登录、后台 API 授权和统计/内容只读公开接口；随后发布前端页面。为店员创建账号、初始权限默认全关，店主显式勾选后才开放模块与敏感动作。
4. 回滚应用时保留新增字段和表，不执行降级删除。旧版本不理解 STAFF 的权限模型；若需要恢复旧版本，应先停用店员账户并限制管理端入口，只恢复为已知 OWNER 登录，不允许旧应用继续接受店员 token。
