# Design

## Context

动机和用户可见行为参见 `proposal.md` 与 `specs/buyer-profile/spec.md`。当前后端已有买家账户表（包含 `nickname`、`avatar_url`）、JWT 买家角色和 `/api/v1/buyer/**` 的角色保护；尚无地址表或买家资料维护接口。前端已有 Vue Router、Pinia、Axios 和 Element Plus，`/account` 目前是单一信息展示页。数据库迁移由 Flyway 管理，测试环境另有 H2 schema 初始化脚本。

## Goals / Non-Goals

**Goals:**

- 通过买家专属 API 实现个人资料、头像、密码和地址操作，并从认证主体确定数据归属。
- 让地址上限、默认地址唯一性和手机号唯一性在并发请求下保持一致。
- 复用现有前后端栈、统一 API 错误格式及已有账户字段，采用可回滚的增量数据库迁移。
- 头像文件以本地配置目录持久化，数据库只保存受控的头像引用。

**Non-Goals:**

- 管理员用户管理、账户注销、短信验证、地区字典/级联数据服务、邮编、第三方文件存储或图片裁切服务。
- 修改全站认证机制、JWT 角色模型或订单数据模型。

## Decisions

### Buyer API boundaries

- 使用现有 `/api/v1/buyer/**` 买家角色授权，并沿用 `JwtAuthenticationToken` subject 作为买家 ID，不接受客户端传入的 owner ID。
- 建议接口边界为 `GET/PATCH /api/v1/buyer/profile`、`POST /api/v1/buyer/profile/avatar`、`PUT /api/v1/buyer/profile/password`，以及 `GET/POST /api/v1/buyer/addresses`、`GET/PUT/DELETE /api/v1/buyer/addresses/{addressId}` 和 `PUT /api/v1/buyer/addresses/{addressId}/default`。请求和响应使用专用 DTO，密码哈希、存储绝对路径和其他内部字段不出现在响应中。
- 继续使用统一 `ApiResponse` 与现有校验错误格式。手机号格式规则沿用注册时的校验口径，唯一性由预检查提供友好冲突信息并由数据库唯一索引兜底；昵称和地址字段长度在 DTO 与数据库列约束间保持一致。
- 密码变更验证当前密码，复用注册的密码长度/编码策略和 BCrypt。成功响应后前端清除 Pinia/localStorage 会话并跳转登录页；本次不增加 JWT 撤销机制，旧 token 仍受原过期策略约束。

### Address persistence and invariants

- 新增 Flyway `V2` 地址迁移，不改写已部署数据库可能已执行的 `V1`。`user_address` 保存买家 ID、收货人、联系电话、省、市、区县、详细地址、`HOME`/`COMPANY` 标签、默认标记和审计时间，并建立买家 ID 查询索引及必要外键。测试 schema 同步更新。
- 读写地址时始终以 `(address_id, buyer_id)` 限定记录；不存在或不属于当前买家的 ID 使用统一拒绝语义，不返回被访问地址的任何字段。
- 新增地址和设置默认地址通过事务串行化同一买家的写操作：先锁定该买家的账户行，再统计/更新地址。新增前检查总数小于 5；设置默认时在同一事务中清除其余默认标记并设置目标地址。数据库唯一键继续保证手机号不重复；地址默认约束由账户行锁和事务维护。
- 新地址默认设为非默认，除非该次新增请求显式要求设为默认。删除默认地址不自动提升其他地址。

### Avatar storage and delivery

- 将头像文件写入本地配置目录，目录通过环境配置提供，启动时确保目录存在；文件名使用随机不可猜测标识，不使用客户端文件名。`buyer_account.avatar_url` 仅保存应用可访问的相对头像引用，不保存服务器绝对路径。
- multipart 请求在 HTTP 层限制单文件 5 MiB；同时检查声明 MIME 类型与文件签名，仅接受 JPEG、PNG 和 WebP。拒绝空文件、伪造扩展名、无效内容及超限请求，统一返回验证错误。
- 通过专用只读头像 URL 暴露文件，不开启目录列表，不允许路径穿越，也不将上传目录映射为可执行内容。旧头像替换时先写入新随机文件并完成数据库更新，再尽力删除旧文件；若数据库更新失败则清理新文件。文件删除失败只留下不可引用的孤立文件，不回滚已成功的资料更新。
- 备选方案：将图片存入数据库会放大数据库备份和响应负担；第三方对象存储超出单机部署范围，因此使用可配置本地目录。

### Frontend personal center

- 将 `/account` 扩展为带左侧导航的个人中心，设置个人资料、收货地址、账户安全子路由，默认进入个人资料。保持现有商城顶栏和视觉规范，主区域使用 Element Plus 表单、表格/列表、上传和确认对话框控件。
- 页面进入时调用资料 API作为真实数据源，不把注册或登录时 JWT 会话中的旧 displayName 当作可编辑资料。成功保存资料后同步更新 Pinia 会话中的展示名；手机号、头像和地址以 API 响应为准。
- 地址表单用三个文本输入框录入省、市、区县，不引入地区数据包。地址标签用固定选项“家/公司”；第五个地址达到上限后隐藏/禁用新增入口，同时仍展示服务端拒绝结果。
- 头像上传在前端限制格式和大小并展示预览及错误；服务端校验是最终约束。密码成功变更后清除会话并导航到登录页。
- 备选方案：将三类功能置于单页会增加表单状态和页面长度；独立个人中心子路由保留清晰导航，也便于后续扩展。

### Verification

- 后端集成测试覆盖未登录/错误角色拒绝、买家只能操作本人数据、资料唯一性与不可修改用户名、头像格式/大小校验、密码原密码校验、地址 CRUD/标签/字段校验、5 条上限以及默认地址切换和删除行为。
- 对同一买家的并发地址新增/默认变更增加事务级验证或可重复的服务集成测试，确认上限和默认标记不被并发请求突破。
- 前端至少运行类型检查和生产构建；关键个人中心路由覆盖未登录跳转及角色守卫。

## Risks / Trade-offs

- 多进程或不遵守账户行锁的写路径可能破坏地址并发约束 → 所有地址新增、删除及默认切换统一经过带账户行锁的 service 事务，并用数据库唯一约束保护手机号。
- 本地文件不随数据库事务提交，进程中断可能留下孤立头像文件 → 采用随机不可变文件名、先写新文件再更新引用，并将清理失败限定为存储泄漏而非错误引用；当前单机部署不要求跨主机共享目录。
- 仅校验 MIME 或扩展名无法阻止伪装文件 → 服务端额外验证文件签名并拒绝未知内容；头像以静态资源方式只读提供。
- 当前 token 中的显示名可能与新资料不同步 → 个人中心以资料 API 为准，资料更新后同步本地展示名；权限身份只依赖 token subject 与 role。
- 用户手机号不经短信验证，无法证明号码当前归属 → 该限制是本次确认的范围，接口仍校验格式与唯一性，后续可独立增加验证流程。

## Migration Plan

1. 先部署兼容旧数据的 Flyway 地址表迁移及头像目录配置；现存买家 `avatar_url` 可为空，无需回填。
2. 部署后端资料、地址、头像与密码接口，再发布依赖这些接口的前端个人中心。
3. 配置头像本地目录并确认应用读写权限与静态读取路径；未配置上传存储时服务启动应明确失败或禁用上传，而不能把文件写入临时目录。
4. 回滚时可回退前后端代码并保留新增地址表与头像文件，避免误删买家数据；若必须移除功能，应另行制定显式数据保留/导出策略，不在自动回滚中删除地址。
