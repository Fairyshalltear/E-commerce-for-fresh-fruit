# Design

## Context

动机与用户可见范围见 `proposal.md`，行为契约见 `specs/shopping-cart/spec.md` 和 `specs/user-accounts/spec.md`。当前系统已有 `buyer_account.status`、JWT 角色授权、SKU/商品状态、`sku_inventory` 可售量、管理员操作日志和 Vue 商城/后台布局；购物车表和管理员买家 API 尚不存在。JWT 当前签发后不再读取账户，故立即撤销要求增加请求期账户校验。

## Goals / Non-Goals

**Goals:**

- 持久化买家购物车与最近接受的 SKU 单价基准，并在并发更新下保持数量和选择状态一致。
- 购物车及结算校验始终以当前商品/SKU 状态、价格和 `on_hand - reserved` 为准；购物车操作不更改库存。
- 买家禁用或密码重置后，旧 JWT 不可在重新启用后复活。
- 管理账户操作与审计记录同事务提交，且响应和日志均不包含密码材料。

**Non-Goals:**

- 本次不实现订单、支付、库存预留、运费策略或订单统计。
- 不管理管理员账户，不在买家管理详情中显示订单或收货地址。
- 不增加购物车跨设备合并、匿名购物车或批量导入导出。

## Decisions

### Cart persistence and validation

- 新增 `cart_item`，保存 `id`、`buyer_id`、`sku_id`、`quantity`、`selected`、`accepted_unit_price` 和时间戳；对 `(buyer_id, sku_id)` 建唯一约束并建立买家查询索引。外键关联买家和 SKU。加入已有 SKU 时在事务内锁定/更新唯一行并累加数量，防止重复行；数量必须为正整数且不得高于当前可售量。
- 所有商品状态、SKU 状态、分类可见性和库存信息复用目录/库存数据源；当前可售量为 `on_hand - reserved`。下架、停用或库存不足不删除购物车行，以便买家处理。购物车金额由当前单价与有效已选数量按十进制定点数在后端计算，前端只展示服务端金额，不以浮点数作为事实来源。
- `accepted_unit_price` 在添加或买家确认新价时更新。结算校验发现当前单价不同则返回价格变化条目并阻止通过；明确确认后更新基准，再重新校验。选择状态、全选和数量修改均由买家 API 持久化；条目删除采用所有者条件，避免跨账户访问。
- 新增买家 API：读取购物车、添加 SKU、修改数量、删除条目、更新单条/全量选择、确认当前价格、校验已选条目。统一使用现有 `ApiResponse` 和 `/api/v1/buyer/**` 的角色保护。校验只返回最新金额、运费零和可购买结果，不创建订单或预留库存。

### Buyer administration and immediate token revocation

- 新增管理员买家分页 API，关键词对用户名、手机号、昵称做转义后的包含匹配，可选状态筛选；详情响应采用专用 DTO，仅包含基础资料、状态和 `created_at`。不得序列化 `BuyerAccount` 实体或密码字段。
- 新增受 ADMIN 保护的状态变更及密码重置 API。状态仅允许 0/1；重复设置相同状态是无操作，不写重复成功日志。临时密码沿用注册密码策略（8 至 72 字节/字符边界按既有校验口径）；服务端 BCrypt 编码。操作和 `AuditService.record` 在同一事务内提交，审计字段仅含管理员、操作类型和买家目标 ID。
- 在 `buyer_account` 增加非空 `credential_version`，默认 0；签发买家 JWT 时加入该版本 claim。禁用账户和重置密码时递增版本。JWT 认证转换/校验阶段按 subject 加载买家，要求账户启用且 claim 与数据库版本相同；不匹配时认证失败。这样禁用后即使以后重新启用，旧令牌仍因版本过期而不能复活。重新登录签发当前版本的新令牌。
- 迁移采用新增 Flyway V4，不改写已应用的 V1-V3；测试 schema 同步增加新字段和 `cart_item`。对认证校验采用 fail-closed：账户查询异常时拒绝受保护请求。

### Frontend integration

- 商品详情仅对买家或未登录访客展示加入购物车操作；访客触发时引导登录并在登录后返回原商品。管理员不显示买家购物操作。
- 商城导航增加购物车入口；购物车页呈现当前 SKU、价格、库存/失效状态、数量、选择控件、全选、删除和已选合计，并提供校验结算操作。价格变化需显式确认后才能重新校验通过。
- 管理端增加买家管理导航和路由；列表提供关键词、状态筛选和分页，详情按确认范围展示基础资料/状态/注册时间。禁用/启用及临时密码重置均通过带确认的操作完成，并显示结果或服务端错误。
- 复用现有 Axios、分页、错误提示和 Element Plus 组件，不增加前端依赖；令牌失效继续通过现有全局 401 处理返回登录入口。

## Risks / Trade-offs

- 每个买家 JWT 请求需查询账户状态和版本 → 增加一次数据库读取，但能兑现即时撤销；先采用数据库权威校验，不引入缓存一致性问题。
- SKU 并发加购可能导致超库存 → 在事务中锁定购物车行及 SKU/库存数据，并以可售量复核；数据库唯一约束兜底并发插入。
- 目录可见状态涉及商品、SKU 和分类多表 → 抽取或复用现有目录可售校验，确保购物车读取、变更和结算使用一致规则。
- 单价在购物车中保留接受基准 → 价格变更需买家确认，避免静默改变结算预期；不将该基准用于历史订单快照。
- 用户列表搜索可能扫描账户表 → 限制页大小、为常用排序/过滤字段建立合适索引，并使用参数化/转义的关键词匹配。

## Migration Plan

1. 增加 V4：为买家增加默认版本号并创建购物车表、外键、唯一约束和索引；同步 H2 测试 schema。
2. 部署后端认证校验、买家账户管理和购物车 API；旧买家令牌在迁移后按默认版本 0 继续有效，直至禁用或密码重置递增版本。
3. 部署前端商品详情、购物车和后台买家管理路由；验证买家/管理员角色边界、审计事务、旧令牌撤销及数据库迁移。
4. 回滚应用可回退前端/后端代码；已应用的 V4 不自动删除购物车或版本数据，采用向前修复迁移以避免丢失买家数据。
