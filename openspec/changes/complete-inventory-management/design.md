# Design

## Context

动机参见 `proposal.md` 的 Why，行为契约参见两个增量 spec。

- 后端使用 Spring Boot、MyBatis-Plus、MySQL 和 Flyway；`sku_inventory` 已有 `on_hand`、`reserved`、`low_stock_threshold`、`version`，数据库约束实物不小于预留。
- `InventoryService` 目前负责商品初始库存和商品编辑调整；`OrderService` 直接预留/释放库存并在发货时生成 `ORDER_DISPATCH` 流水；`AfterSaleService` 验收后生成 `RETURN_RESTOCK` 流水。流水已有数量和审计字段，业务单号目前主要写在原因文本中。
- `CatalogDtos.SkuRequest` 目前要求每次保存提交库存和阈值，并禁止未知字段；商品编辑保存会按库存版本校验并调整数量。本次需要同步替换此契约，而非只隐藏输入框。
- 前端已有管理员布局、路由守卫、分页及错误组件，没有独立库存页面。现有订单并发测试和商品库存测试需要保留或适配。
- 主 spec 尚未同步，历史变更包含 `inventory-control`、`fruit-catalog`。本变更沿用路径，但以 ADDED 表达待注册契约；商品初始库存规则替代历史直接编辑规则，不能在未来归档多个历史变更时无审查覆盖新规则。
- 用户已选择简单采购、退供、草稿后直接生效、后台预警、盘点修正和商品仅设置初始库存。完整提案仍待用户审核，当前不授权实现。

## Goals / Non-Goals

**Goals:**

- 保持单一库存真值，新增单据是库存变化的来源，不另建一套可售库存。
- 通过单据状态锁、库存行锁和版本检查保证原子过账、重试幂等及盘点快照可复核。
- 在普通商品编辑时解耦库存版本，避免订单预留影响仅修改描述或价格的保存。
- 将新增作业和已存在订单/售后流水统一展示，保留历史记录。

**Non-Goals:**

- 不引入外部供应链、审批、消息推送或库存计价依赖；业务范围见 proposal。
- 不为订单发货或售后验收再建可人工确认的库存单据，不改变既有订单/售后状态机。
- 不改写已经应用的 V1–V5 迁移，不自动初始化商品演示数据。

## Decisions

### 1. 库存数量与四类作业

所有数量按 SKU 包装单位计数。采购/客户退货入库增加 `on_hand`；退供减少 `on_hand` 且不影响 `reserved`；销售发货同时减少两者。下单、取消和未发货退款仅改变预留，不生成实物数量流水。采用此口径可以复用当前商城可售公式，避免付款就提前扣实物。

例：实物 30、预留 8、可售 22。采购入库 20 后为 50/8/42；销售发货 8 后为 42/0/42；客户退货可入库 3 后为 45/0/45；退供 5 后为 40/0/40。仅保存草稿不改变这些值。

备选是所有库存页面手工登记销售和客户退货，但会重复既有履约库存变更，已按用户决定排除。

### 2. 单据模型与生命周期

新增 `inventory_document` 与 `inventory_document_item`，承载 `PURCHASE_IN`、`SUPPLIER_RETURN_OUT`、`STOCKTAKE` 三种人工作业。状态仅为 `DRAFT`、`POSTED`，主表保存唯一单号、供应商、参考采购单号、原因/备注、版本、创建及确认管理员/时间。草稿可修改和删除，POSTED 不可改删；业务单号创建时分配且不复用，参考采购单号只是人工文本，不具有外部防重语义。

每张单据 1–100 个不同 SKU。采购和退供数量为 1 至 INT 上限的整数；采购必须有供应商名称，退供必须有供应商和原因。供应商最长 100、参考单号最长 100、原因/备注最长 200；不引入金额字段。累加采用扩大范围计算并检查 INT 溢出。

明细保存 SKU 与商品/规格快照。采购/退供草稿保存数量，确认时保存前后实物和预留。盘点明细另外保存账面实物/预留/可售、库存版本、实盘和差异；快照由服务端读取得到，禁止客户端伪造账面数量。确认时冻结最终展示快照。未变化盘点保留明细，不产生零差额流水。

统一模型减少重复状态机，列表按类型分开，盘点专有字段不对普通出入库用户展示。备选是独立三套单据表，会重复幂等和草稿逻辑，当前业务规模不需要。

### 3. 原子确认、库存锁和冲突处理

确认先锁单据，读取状态：若已 POSTED，返回既有详情，库存不再变化；若为草稿，校验请求单据版本，锁明细，再按 SKU 标识升序取得库存行锁。全部校验通过后更新数量/版本、生效状态、明细结果、流水和成功审计，任一失败整体回滚。

采购/退供是相对数量，在确认时根据当前库存计算，不要求草稿创建时库存版本仍一致；退供基于当前可售量拒绝超额。盘点是绝对实盘数，必须检查保存的库存版本，发生预留、释放或数量/阈值变化也视为快照已过期，返回 `409 INVENTORY_CONFLICT`。

盘点冲突页保留原快照和实盘输入，同时展示最新账面值。显式“刷新账面数据并复核”动作重新取得服务端快照并更新草稿版本，保留实盘输入但要求管理员再次确认。禁止确认操作暗中刷新并直接覆盖最新库存。

新增人工作业事务使用当前数据读取策略（READ_COMMITTED），商品/SKU 资格在取得库存锁后校验；仅锁本单据与库存，不在持有库存锁后反向申请订单、售后或商品锁。已有停用/删除操作也受库存锁约束。共有库存变化辅助逻辑接收已经锁定的库存行，仅执行数值更新及流水写入，不另行取得上层业务锁；现有业务流程继续负责自身状态锁。采购拒绝停用或删除对象，退供和盘点可处理剩余历史库存。

备选是所有作业无版本直接覆盖数量，会造成盘点覆盖并发入库；或草稿时一直锁库存，会阻塞正常销售，均不采用。

### 4. 统一流水与业务来源

复用 `inventory_movement`，扩展可空 `source_type`、`source_id`、`source_item_id`、`source_no` 及商品/规格快照字段，保留原 `type`、数量、原因、管理员和审计关系。新增采购、退供、盘盈和盘亏类型；已有 `ORDER_DISPATCH` 在界面标为销售出库，`RETURN_RESTOCK` 标为客户退货入库，`INITIAL` 和 `PRODUCT_EDIT_ADJUSTMENT` 独立展示。

订单发货和售后验收在原事务中传入结构化来源，不重新触发库存作业。预留变更继续更新库存版本但不计入实物流水。既有销售/退货原因中的单号仅在与真实订单/售后及 SKU 关联精确且唯一匹配时补全来源；不能确认的旧记录保留文本，不凭猜测填入单据关联或冻结快照。

入库/出库页面提供类型切换：采购/退供显示草稿和已生效单据，客户退货/销售显示既有业务产生的流水，查看后跳转售后/订单。待处理售后或待发货订单仍在原业务页面处理。通用流水页包括初始和盘点等全部实物变动。

备选是通过流水原因永久解析单号，无法保证长期可追溯；或复制订单/售后库存单据，会引入两次生效入口，均不采用。

### 5. 商品保存契约

商品响应保留当前库存只读字段。SKU 保存请求按 `id` 分支：新 SKU 提交规格、价格、状态和 `onHand` 初始数，服务端阈值初始化为 0；已有 SKU 只提交标识、规格、价格和状态，不接受 `onHand`、`lowStockThreshold`、`reserved` 或 `inventoryVersion`。移除商品请求的 `adjustmentReason`。

现有 SKU 修改不调用库存数量调整，商品版本继续防并发商品编辑，库存锁继续用于停用、移除及删除的预留保护。新 SKU 初始库存与商品同事务提交。旧客户端提交库存字段返回 `400 VALIDATION_ERROR` 并提示新契约；不静默忽略字段，避免客户端误认为库存已调整。

备选是继续接收旧库存值但不写入，会隐藏调用错误；保留旧库存写入口则违背用户决定。需要前后端同版本更新，并同步所有测试数据构造器。

### 6. 库存查询与后台预警

库存列表、汇总和 SKU 选择器在数据库端使用统一关联及过滤条件、稳定排序和有上限的分页，不加载全量商品再过滤。默认总览排除逻辑删除商品、包含下架及停用 SKU；删除数据通过状态筛选查历史。可售为零和低库存筛选可重叠，不将它们错误视为互斥条件。跨不同 SKU 的数量汇总只是包装件数统计，不表示重量或资产金额。

低库存条件为商品未删除、SKU 启用、阈值 > 0 且可售 < 阈值；下架备货仍预警，分类停用不影响仓库库存预警。独立 count 查询支撑管理员菜单，预警列表复用库存分页过滤。阈值更新带库存版本，同事务更新版本和审计，但不新增数量流水。

管理员后台进入时、页面恢复可见时和可见状态每 60 秒刷新 count；预警页同时刷新列表，其他库存操作成功触发相关查询刷新。离开后台清理定时器，避免后台请求堆积。失败保留上次值并标记无法刷新，不显示假零；初次失败显示未知并提供重试。

备选是持久化提醒消息或 WebSocket，当前无通知已读需求，轮询满足已选后台提醒范围，不承诺即时推送或提醒历史。

### 7. 接口与前端结构

新增 `/api/v1/admin/inventory`，沿用统一响应及 ADMIN 权限：

| 接口 | 作用 |
|---|---|
| GET `/stocks`、`/summary`、`/sku-options` | 库存分页、全匹配汇总、作业选 SKU |
| GET `/movements` | 流水分页和业务来源 |
| GET `/alerts/count` | 当前后台预警数；预警明细通过 stocks 低库存筛选读取 |
| PATCH `/stocks/{skuId}/threshold` | 带库存版本更新阈值 |
| GET/POST `/documents`、GET/PUT/DELETE `/documents/{id}` | 列表、创建草稿、详情、修改/删除草稿 |
| POST `/documents/{id}/post` | 携带草稿版本确认生效；已生效结果幂等返回 |
| POST `/documents/{id}/refresh-snapshot` | 盘点草稿显式刷新账面快照，保留实盘输入 |

分页默认 20、范围 1–100，日期区间和类型枚举校验；不存在返回 404，无权限 401/403，状态、版本、库存不足返回 409，前端保留输入并展示服务端具体信息。操作人取 JWT，不接受客户端覆盖。

前端新建库存 API 类型和 `/admin/inventory` 子页面：总览、入库、出库、预警、盘点、流水以及单据详情/编辑。复用 `PageStatus`、`PagePagination` 和现有样式。单据确认弹窗展示类型、数量、供应商/来源和库存影响；盘点展示差异及是否低于预留。商品编辑的已有库存只读并链接库存管理，新 SKU 显示“初始库存”。长表格在手机端采用局部滚动或卡片，不能导致整个页面横向溢出。

## Risks / Trade-offs

- [商品 API 不兼容旧负载] → 前后端同步升级、更新测试构造器和 API 文档，保留明确校验提示。
- [历史来源只有原因文本] → 仅精确验证的关联可补全；无法验证则保留原文，不伪造历史快照。
- [预留变化也会使盘点版本过期] → 显式刷新复核保护真实盘点，代价是活跃销售期间可能多次复核；不冻结订单。
- [单据修改和库存并发] → 状态锁、单据版本、升序库存锁和专项并发/回滚测试；共有辅助逻辑不增加上层反向锁。
- [无批次时无法区分某次采购退供数量] → 参考采购单号仅用于人工追溯，系统只校验当前库存可退数量。
- [轮询提醒存在最长约 60 秒延迟] → 页面恢复可见及业务成功立即刷新，失败显示状态并重试。
- [已生效单据无法直接改供应商或数量] → 原记录保留；本期通过带原因的盘点纠正账面差异，不提供财务冲销或业务单撤销。

## Migration Plan

1. 实现前再次确认最新迁移编号；预期新增 V6，不修改 V1–V5。创建单据主明细表，扩展流水可空来源字段及查询索引，同步测试 H2 schema。
2. 在专用 MySQL 旧库验证 V1–V5 到新版本升级，检查库存值、订单/售后、历史流水和审计保留，重复迁移及 Flyway 校验通过。可验证来源仅按精确唯一关系补全。
3. 发布兼容新 schema 的后端和同步前端，验证新 SKU 初始化、已有 SKU 只读、采购→预留→发货→客户退货→退供→盘点闭环和预警。
4. 应用回滚时保留新增表和字段及已经生效数据，不执行破坏性降库。旧应用会重新暴露库存编辑入口，不能无控制恢复正常写操作；必要时暂停管理员库存写入并恢复到受控版本，依据保留单据/流水核对库存后再开放。
