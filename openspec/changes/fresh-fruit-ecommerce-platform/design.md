# Design

## Context

动机和业务范围参见 `proposal.md`；可观察行为以 `specs/` 下的能力规格为准。当前仓库有 `front-end/`、`back-end/` 目录和 OpenSpec 配置，但尚无应用代码。项目面向毕业答辩，优先保证核心购物、订单、库存和售后闭环可在单机演示；暂不接入真实支付、快递、短信或在线大模型服务。

已确认的关键业务口径：

- 只有买家和管理员两类账户；用户浏览商品无需登录，购物车、下单及个人订单操作需要买家登录。
- 商品按预设 SKU 出售，SKU 份数为正整数；商品保鲜说明不等于库存批次追踪。
- 库存区分实物量和预留量；下单预留，未付款取消或超时释放，发货时扣减实物量及预留量。
- 未付款订单默认 15 分钟后自动取消；全场包邮；模拟支付不触发外部支付渠道。
- 库存按 SKU 汇总，不实现批次、效期、临期预警或逆向物流追踪。
- AI 使用提前准备的本地中文 ONNX embedding 模型、MySQL 向量存储和检索模板，不调用在线生成模型。

## Goals / Non-Goals

**Goals:**

- 用一个前端应用提供商城和管理端两种布局，并通过后端角色授权隔离操作。
- 以事务保持订单、库存预留、支付模拟、发货和售后退款之间的数据一致性。
- 让答辩环境在模型文件准备完成后不依赖运行时外网服务。
- 为模块化实现提供可迁移的数据模型、接口边界和可重复的本地启动方式。

**Non-Goals:**

- 生产级支付、第三方物流、短信验证、商家多租户、复杂权限矩阵或云端部署。
- Redis、独立向量数据库、分布式库存、库存批次/临期管理或高并发性能目标。
- 在线 LLM 生成、在线模型配置、图像评价、商家评价回复或自动售后决策。

## Decisions

### Application structure and stack

- 前端在 `front-end/` 使用 Vue 3、TypeScript、Vite、Vue Router、Pinia、Axios 和 Element Plus。商城与管理端共享构建和组件基础，但使用独立路由、布局及导航；管理员路由由登录态和角色守卫保护。
- 后端在 `back-end/` 使用 Java 17、Spring Boot 3.5.x、Spring Web、Spring Security、JWT、MyBatis-Plus、MySQL 8 和 Spring AI ONNX embedding。按 `controller -> service -> mapper` 分层；业务事务、状态转换和授权检查位于 service 层。
- 选择单体 REST API 而非微服务：订单、库存与售后需要数据库事务一致性，单体更易于本地部署、调试和答辩演示。商城 API 使用 `/api/v1/` 前缀；业务错误采用统一 JSON 响应，列表使用分页参数。
- 不加入 Redis。小规模演示数据由 MySQL 承担持久化及查询；超时订单由后端定时扫描处理。

### Authentication and authorization

- 买家账户与管理员账户分表，不建设通用 RBAC 权限配置；后台接口只接受 ADMIN 身份，买家接口从认证主体读取当前买家 ID。
- 买家使用用户名或手机号加密码登录。密码使用 BCrypt 哈希存储；JWT 只携带账户 ID 与角色，不在前端保存明文密码或模型凭据。
- 首个管理员由未提交到 Git 的本地环境变量初始化。初始化逻辑在管理员表为空时执行；后续管理员只能由已认证管理员创建或管理。
- 对用户地址、订单、售后、收藏、购物车、评价和 AI 会话执行资源归属检查，避免依赖前端传入的用户 ID。

### Transaction and inventory model

- `sku_inventory` 保存每个 SKU 的 `on_hand`、`reserved` 和 `low_stock_threshold`。可售量计算为 `on_hand - reserved`；预警依据可售量与阈值比较。
- 提交订单时按 SKU ID 稳定顺序锁定库存记录，在单个事务中校验可售量、增加预留量并写入订单及订单明细快照。任一 SKU 失败时整笔事务回滚。
- 付款、取消、超时、发货及售后退款使用带当前状态条件的事务更新，保证重复请求不会重复释放或扣减。发货在同一事务中扣减 `on_hand` 和 `reserved`，并写一笔库存流水。
- 每分钟扫描超过 `order.unpaid-timeout-minutes` 的待付款订单，默认值为 15；通过状态条件更新保证只取消一次。超时值通过本地环境配置，不要求管理端提供参数页面。
- 订单头和明细保存地址、商品名、SKU 规格、单价、数量及金额快照；后续商品改名、改价或改地址不改变历史订单。
- 所有金额使用定点十进制；SKU 数量使用整数。免费配送不产生运费明细。

### Data model

数据库使用 Flyway 管理增量迁移；代码不依赖手工创建表。约 30 张核心表按职责划分如下，字段和索引在实现任务中以外键、唯一约束和访问模式进一步细化。

| 领域 | 核心表 | 用途 |
| --- | --- | --- |
| 账户 | `buyer_account`, `admin_account`, `user_address` | 买家、管理员和买家收货地址 |
| 商品 | `product_category`, `fruit_product`, `product_sku`, `product_image`, `user_favorite` | 两级分类、商品、可售规格、图片和收藏 |
| 购物车 | `cart_item` | 买家与 SKU 的份数及选择状态 |
| 交易履约 | `shop_order`, `order_item`, `payment_record`, `shipment`, `shipment_event` | 订单快照、模拟支付、运单及手工物流轨迹 |
| 售后 | `after_sale_request`, `after_sale_item` | 退款/退货申请、明细、审核和处理状态 |
| 库存 | `sku_inventory`, `inventory_movement`, `stocktake`, `stocktake_item` | SKU 汇总库存、流水和盘点记录 |
| 评价 | `product_review` | 已购 SKU 的评分和文字评价 |
| AI | `ai_knowledge_document`, `ai_knowledge_chunk`, `ai_conversation`, `ai_message`, `ai_feedback`, `ai_sensitive_term` | 知识文档、切分与向量、会话消息、反馈和敏感词 |
| 站点内容 | `homepage_banner`, `announcement` | 首页轮播图和公告 |
| 审计 | `admin_operation_log` | 后台敏感操作审计记录 |

关键约束：买家用户名/手机号唯一；同一买家同一 SKU 只有一条购物车行；同一订单明细最多一条评价；支付和库存流水带有来源业务标识以避免重复记账；金额和密码不以不安全类型存储。管理员重置买家密码和其他敏感管理操作均写审计记录，但日志不得包含密码、JWT 或 API Key。

### Local AI retrieval

- 知识内容以文档形式维护，来源包括水果知识、FAQ、售后政策及管理员维护的商品知识；每份文档按段落切分为 `ai_knowledge_chunk`。
- 本地中文 embedding 模型从本地模型目录加载。模型权重不提交 Git；提供预下载与启动前校验步骤，答辩运行时不得尝试在线下载。
- 每个知识块保存向量 JSON、模型标识和维度。提问时在 Java 后端生成查询向量，从 MySQL 读取启用知识块并计算余弦相似度，取前若干结果交给场景模板组织答复。以当前预计的小规模知识库为前提，不建设向量索引。
- 商品事实推荐由上架状态、SKU 库存和商品元数据过滤；订单/物流问题直接按已认证买家身份查询关系数据，不从 embedding 检索中推断订单状态。
- 若检索分数低于阈值，返回无可靠答案提示。知识编辑、发布、停用后重建或清除关联向量，避免旧内容继续命中。

### Files, configuration, and local deployment

- 商品图片和轮播图存本地上传目录，MySQL 只存相对路径；上传目录及本地模型目录加入 `.gitignore`，并提供演示图片或种子数据以便初始化。
- 业务配置和密钥通过未提交的本地环境文件提供；提交 `.env.example` 只含变量名和无敏感示例。管理员首登信息、JWT 密钥、数据库密码及模型权重不进 Git。
- 提供前端开发服务器、Spring Boot 服务和 MySQL 8 的本地启动说明；Docker Compose 可用于启动 MySQL，但不作为唯一运行方式。应用本身不要求 Docker、Redis 或云服务。
- Git 以单仓库管理 `front-end/`、`back-end/`、迁移、种子演示数据及 OpenSpec 制品。每个已完成并验证的功能模块单独提交到 `main` 并推送至指定 GitHub 远端；不推送凭据、本地上传文件或模型权重。

## Risks / Trade-offs

- 本地 ONNX 推理增加模型体积和内存占用，首次准备也需下载 → 预先准备模型文件，提供校验脚本，并在答辩机上提前验证启动与中文检索质量。
- 将全部向量从 MySQL 读取并在 Java 中计算相似度不适用于大规模语料 → 将知识块规模限定为毕业答辩演示，未来数据量增长时再迁移到专用向量索引。
- 不接真实支付和物流意味着只能验证系统内部状态流转 → 在界面明确标记“模拟支付/模拟物流”，保留支付记录和可审计物流事件。
- 订单与库存并发操作可能导致超卖或重复扣减 → 使用数据库事务、库存行锁、状态条件更新和幂等来源键，并为并发下单、超时释放、发货及退款增加集成测试。
- 本地图片目录不适用于多实例部署 → 当前按单机演示约束选择；如部署到多实例环境，再迁移到对象存储。
- 商品、库存和 AI 内容仅有审计信息可能包含业务数据 → 日志字段采用白名单，不记录凭据、完整会话内容或买家密码。

## Migration Plan

1. 建立 Flyway 初始迁移和后续按模块递增的 schema 迁移；本项目无现存业务数据库，无需导入旧数据。
2. 配置本地 MySQL、管理员初始化变量、图片目录和 ONNX 模型目录；运行迁移与演示种子数据脚本。
3. 按模块实现并验证账户、商品、交易库存、履约售后、评价、AI、站点和统计能力；每个完成模块通过相关测试后提交并推送 GitHub。
4. 答辩前在目标机器预下载并校验 embedding 模型，按 README 启动并完成买家下单、支付、发货、收货、评价及售后演示路径。
5. 如回滚，使用 Git 回退到上一个已验证模块提交；数据库采用向前修复迁移，不自动删除已写入的订单或审计数据。
