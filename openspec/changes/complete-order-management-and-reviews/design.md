# Design

## Context

动机与用户范围见 `proposal.md`，行为契约见 `specs/`。现有实现是 Vue 3/Vite 前端与 Spring Boot 3、Java 17、MyBatis-Plus 后端；Flyway 维护 MySQL 8 schema，后端集成测试以 H2 为主。买家与管理员通过角色化 JWT 隔离，控制器从 JWT subject 读取账户 ID。购物车结算目前只校验，`sku_inventory` 已维护 `on_hand`/`reserved` 并提供行锁，评价查询和 `product_review` 表已存在，但无订单、支付、发货、售后或评价写入流程。

## Goals / Non-Goals

**Goals:**

- 使结算、库存预留、支付、发货、退款/退货、评价写入与审计具有可回滚且可测试的一致性边界。
- 复用现有鉴权、分页响应、统一错误、商品可售校验、库存流水和前端页面模式。
- 保留订单购买时数据及售后/评价处理记录，支持 MySQL Flyway 迁移和 H2 集成测试。
- 为真实物流接入保留明确的替换点，同时确保当前本地/答辩环境不依赖外部服务。

**Non-Goals:**

- 不连接支付宝/微信真实支付、银行退款、真实快递查询或回调。
- 不实现自动物流事件同步、运费计价、优惠券、拆单、分仓、退货上门取件或客服会话。
- 不提供买家评价编辑、买家删除、评价图片、追评或商家回复。
- 不在本次新增独立支付服务、消息队列、Redis 或通用工作流引擎。

## Decisions

### 1. 以独立业务实体和状态事件表达订单履约

增加订单头 `shop_order`、明细 `order_item`、支付/退款流水、发货记录、物流节点和订单状态事件；售后申请及其明细独立存储。订单头保存唯一订单号、买家、状态、商品金额/运费/总额、收货人/电话/地区/详细地址快照和关键时间。明细保存商品名、SKU 规格、图片、成交单价、数量、实付小计及已退款/已发货/已退货数量等必要快照与累计量。关联商品/SKU ID 用于追溯，但历史展示不依赖当前商品资料仍存在。

买家订单筛选继续使用六个主状态（待付款、待发货、待收货、已完成、已取消）；支付、部分退款和售后阶段由支付/售后记录及状态事件表达，避免把售后流程压入单一订单状态。全额未发货退款完成后将订单标记为已取消并记录退款原因；部分退款仅释放对应未发货明细的库存预留，剩余明细仍可履约。退货退款发生在已完成订单上，不回退订单完成状态。

状态事件采用追加记录，包含前后状态、事件类型、操作者（买家/管理员/系统）、说明和时间。订单当前状态用于列表过滤，事件表为详情时间线；物流节点单独存储运单相关状态描述与发生时间，并按发生时间和稳定 ID 排序。

### 2. 在一个数据库事务内提交结算并预留库存

购物车与立即购买共用确认和下单服务。立即购买把 SKU/数量作为一次性结算输入，不先写购物车。确认页数据只作预览；最终提交时服务端重新验证地址所有权、商品/SKU/分类可售状态、当前价格及购物车接受价、数量和可售库存。

下单事务按 SKU ID 升序锁定库存行，校验 `on_hand - reserved`，随后创建订单及快照、增加 `reserved`、写入创建事件，并只删除本次购物车来源条目。任一检查或写入失败整个事务回滚。对重复下单增加客户端请求幂等键及买家范围唯一约束；相同键返回原订单，避免刷新/重试生成重复单。多行锁定固定排序以降低死锁风险。

预留只改变 `reserved`，不写实物库存流水。取消、超时和已发货前退款以订单/明细状态和累计预留为依据释放一次。发货只针对仍待履约数量，在同一事务中减少 `on_hand` 与 `reserved`，并沿用管理员操作审计及库存流水。退货收货仅增加管理员确认可重新入库的实物数量并写流水。所有库存变化使用 `InventoryService` 可复用的事务边界或等价的受控方法；不得从订单服务绕过库存约束直接更新库存。

### 3. 将模拟支付和退款作为本地策略，不模拟外部副作用

支付记录保留订单号、支付渠道、模拟结果、金额和时间。支付宝/微信是可见渠道选项；买家在本地确认后选择成功、失败或取消结果，不向渠道发请求。仅成功结果在锁定待付款订单后写成功支付记录并将订单置为待发货；失败/取消只记尝试结果并保持订单和预留。状态条件更新及支付幂等键阻止重复付款。

退款通过单独的模拟退款记录表达，金额由成交单价与获批数量计算，不触发渠道 API。订单支付金额、累计退款金额、每行申请中/已退款数量需在事务中复核，禁止超额退款及同一数量被并发重复申请。未发货退款批准后释放关联明细的预留；若所有未发货数量已全退，订单转为已取消；否则保留待发货状态并仅履约剩余数量。

### 4. 将超时取消实现为有界、可重入的后台任务

新增 `freshfruit.order.unpaid-timeout-minutes` 配置，默认 15。定时任务按创建时间分批读取到期待付款订单；逐单通过状态条件更新/行锁将订单从待付款转为已取消，释放尚存预留并写系统状态事件。支付与超时并发时只允许一个状态转换提交，另一个观察新状态后无副作用退出。任务需记录异常并继续后续订单，避免单条坏数据阻断整批处理。

### 5. 售后按申请明细和数量计算权益

申请头保存申请人、订单、类型、原因、说明、金额、状态、审核人/意见和时间；申请明细关联订单明细并保存申请数量、快照单价。申请时锁定订单及相关明细，确认状态、7 天边界和可申请剩余量；处于待审或已批准未完成状态的数量均从可再次申请量中扣除，避免重复占用。

退款申请仅允许已支付且待发货的剩余数量。退货只允许已完成订单在确认收货时间起 7 天内申请。批准的退款直接完成模拟退款；批准的退货进入等待买家寄回，买家只能为本人申请登记一次有效的快递公司和运单号，管理员收到后分别填写退款数量与可入库数量（两者不超过获批数量），再在同一事务中完成退款、库存流水和申请状态。管理员拒绝必须保存理由。全部申请行为由角色校验、订单所有权和状态转换共同保护。

### 6. 复用评价查询，扩展为订单约束的写入与审计删除

评价提交要求订单属于 JWT 买家、订单已完成、明细 SKU 与商品相符且尚未评价。复用 `product_review.order_item_id` 唯一约束作为数据库级防重。评价正文仍按普通文本存储/展示。管理员删除采用逻辑删除字段及删除时间/管理员/原因，并记录一份独立审计快照或结构化审计事件；先锁定有效评价再更新，确保重复操作不重复记审计。公开评价列表、总数、均分及商品详情摘要统一过滤已删除记录，响应 DTO 不包含订单/审计字段。

### 7. 保持 API 与前端边界贴合现有结构

按现有 `/api/v1/buyer/**`、`/api/v1/admin/**`、`/api/v1/public/**` 分组新增订单、支付、售后、管理和评价端点，统一使用 `ApiResponse`、Bean Validation、所有权检查、服务端分页和明确状态冲突错误。管理员审计复用 `AuditService` 的强制事务记录能力；角色由 SecurityConfig 路由规则保护，不接受前端传入 buyer/admin ID。

前端在账户中心新增订单列表、订单详情/售后/评价入口；确认订单与支付使用独立路由并可从购物车或商品详情进入。后台新增订单和售后视图，复用现有筛选、分页、加载/空/错误状态及确认交互。共享订单状态/金额类型和 API 客户端放在 `front-end/src/api/`，不引入新依赖。订单页刷新由服务端状态重取，不依赖仅存于内存的结算状态。

物流以应用内 `TrackingProvider`/端口边界读取与登记物流数据，当前实现为数据库手工轨迹适配器。该接口只隔离将来的轨迹查询来源，不预先设计或启用任何特定供应商；未来真实接入需单独评估签名、凭证、隐私、回调及重试规范。

### 8. 迁移采用新增 Flyway 版本并同步隔离测试 schema

不修改已应用的 V1-V4。新增迁移创建订单/售后/支付/物流事件相关表及索引、约束，并扩展 `product_review` 支持软删除和审计。迁移尽量使用 MySQL 与 H2 MySQL 模式均可运行的 DDL；若 MySQL 专属语法不可避免，则以真实 MySQL Flyway 迁移测试覆盖。同步 `back-end/src/test/resources/test-schema.sql`，既有数据库数据不回填虚构订单。金额使用 `DECIMAL`/`BigDecimal`，时间按项目 `Asia/Shanghai` 配置处理。

## Risks / Trade-offs

- 下单、定时取消、支付、发货和售后可能争用订单/库存行 → 统一锁顺序、短事务、状态条件更新，并增加并发集成测试。
- 部分退款与部分发货同时存在会增加明细数量核算复杂度 → 对每个明细维护数量守恒约束，所有变更先锁订单与明细，测试申请中、已退款、已发货数量边界。
- H2 与 MySQL 在 DDL、锁语义和日期处理上存在差异 → H2 覆盖业务行为，MySQL migration test 覆盖迁移语法，并针对行锁行为写清集成验证边界。
- 手工物流节点不代表真实承运状态 → UI 明确标记模拟物流；适配接口不假定未来供应商行为。
- 评价删除必须在公开统计即时生效且可追责 → 将有效标志与审计写入同一事务，验证列表/摘要/总数同步排除并保留审计快照。

## Migration Plan

1. 添加新 Flyway 迁移和对应测试 schema；运行 MySQL 迁移验证及现有后端测试。
2. 先部署后端 API、任务和新表，再部署前端入口；旧购物车、商品详情和公开评价接口保持兼容。
3. 对新买家订单流程、管理员履约/售后及评价治理执行集成验收，确认旧商品和地址管理未回归。
4. 回滚应用代码时保留已迁移表和业务记录，不自动删除订单/支付/审计数据；后续修复通过向前迁移完成。

## Open Questions

- 未来接入真实物流供应商时再选择具体厂商、认证方式与回调安全策略；本次以适配端口和手工实现隔离，不影响当前行为或任务范围。
